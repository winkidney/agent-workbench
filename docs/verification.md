# Verification notes

These are maintainer notes on how each feature of Agent Workbench was verified, combining automated tests (Go and Vitest) with manual checks on a real local instance. Sections follow the order in which the work was done, with the newest sections last.

## Passed checks

- Environment for the initial round: Linux with systemd 258.11, Go 1.24.4, Node 24.16.0, Claude Code 2.1.319, Codex 0.167.0.
- Full Go test suite with `-race` and `go vet`; TypeScript check, Vite production build and Prettier check.
- Simulated engine: 100 session cycles, native ID preservation, sleep refused while an approval is pending, expired approvals rejected, regression test for delayed MCP startup.
- Real Codex and Claude each completed a text reply, a manual sleep, a resume with the same native ID, and a stop. Both engines were also initialized concurrently in the same directory.
- 300 systemd cycles (create engine, sleep, resume, stop); the FD count stayed at 9.
- Sleep is refused once a new tool subprocess appears; stopping a session terminates its whole process group. After SIGKILL of the parent service no session or managed preview units remained, and a restart recovered the native ID.
- The final build with the preview readiness check ran 3 more cycles and the same parent-crash test, with the preview served by a real listening Python HTTP server.
- Preview authorization: one-time POST, Host/Origin validation, control cookie isolated from the preview cookie, path traversal and symlinks rejected.
- HTTP Range requests return 206; WebSocket upgrade and bidirectional traffic work through the preview proxy.
- Playwright in a real browser opened a managed Vite page; after a JavaScript edit the iframe showed `HMR verified live` without a manual reload.
- A PNG decoded as 1×1; an MP4 reached readyState 4 with a 1 s duration at 320×180.
- Layout checked at 1280×720 and 390×844; the composer stays inside the viewport.

## Memory observations

| Scope | Observation |
| --- | --- |
| Fresh main service | about 12 MiB RSS (`artifacts/idle.json`) |
| Same main service after 300 cycles | 23,144 KiB RSS (about 22.6 MiB), 9 FDs |
| Main service after a restart | 12,420 KiB RSS |
| Codex cgroup, concurrent initialization | 123,281,408 bytes (about 117.6 MiB) |
| Claude cgroup, concurrent initialization | 138,293,248 bytes (about 131.9 MiB) |
| Isolated Chromium after stress test | about 414 MiB PSS, plus about 86 MiB for the Playwright controller |

- Agent figures are the instantaneous cgroup usage at initialization (processes plus kernel-accounted memory), not the peak while a model is running. The browser figure is the whole isolated Chrome process tree after repeatedly switching previews, not a per-tab increment.
- The main service meets the idle target of 50 MiB or less; this does not mean the full stack including engines and a browser fits in 50 MiB.
- RSS grew gradually from cold start during the cycles without exceeding the target. This is not proof that there are no leaks under arbitrary long-running load. FD, RSS and failure-cleanup evidence was kept.

## Limitations

- Real models were used to verify text streaming and resume. Permission prompts and interactive-question branches are covered mainly by protocol fixtures and were not exercised against every native tool. Interactive questions were later verified with real models (see "Questions from Claude and Codex"). Other unsupported control requests are never auto-approved.
- Not yet done: a cross-version compatibility matrix, long heavy tool or video workloads, full agent and browser peak-memory curves, and acceptance testing through external tunnels. Some pre-existing local MCP configurations were not logged in or failed to start; the workbench does not rewrite them.

## Follow sessions running in other clients

- Before: a session in use by another client loaded its history once when opened and never updated; the sidebar only refreshed the "in use elsewhere" icon every 10 s. While viewing such a session, telemetry also re-read the entire native file every second through `nativeUsage` (the largest local Codex rollout was 1.3 GB, the largest Claude transcript 70 MB).
- Approach: while a page views a session, its SSE connection follows the native transcript read-only, at most once per second, and pushes only new or changed records (`event: external`). Claude uses an incremental index that reads only new bytes and reuses the existing main-branch selection. The Codex rollout is an internal format, so a resident read-only app-server reads the latest two turns (on a 1.3 GB thread the first call took 0.48 s and later calls 10–20 ms, and it sees new items while another process is writing). Running state comes from the end of the transcript: Codex `task_started` / `task_complete` / `turn_aborted`; Claude from the last message (`stop_reason`, a pending prompt, `[Request interrupted`). The first read scans back from the end of the file with a window that starts at 1 MiB and doubles. A branch rollback or a gap makes the frontend reload. Usage reading is now incremental with a byte-level prefilter.
- Also fixed: when an `attachment` record followed a parallel tool result, the history reader treated that result as an abandoned branch and the tool showed as interrupted. It now only checks whether a message continues from it.
- Not possible: token-by-token streaming of the other client's reply (the CLI does not write increments to disk), seeing its pending approvals (not written until handled), and approving or sending on its behalf.
- New Go race tests: running-state rules (sidechains ignored, interrupts, non-marker Codex records do not affect state); the scan-back window crossing 1 MiB to find the prompt; partially written lines are not consumed; re-read after truncation; incremental index matches a one-shot read; the follow flow (first round sends only state, first change sends the tail page, later only new records, nothing sent without changes, branch rollback requests a reload, final state sent after the other client releases the session); incremental usage; attachments not affecting parallel results. New Vitest tests: follow merges without duplicates and match the full history; wrap-up at turn end.
- Real data (isolated dev instance): a Claude session running in a terminal was detected as `external_running`. Commands, explanatory text and a README edit made during an observation script appeared within about 1 s; the first change sent 80 records (188 KB), later changes 2–4 each. The status line read "Working… (16m 44s · in another client)" with the turn timer counted from the current prompt, and the header read "Running elsewhere · Read only". `codex exec` running four `sleep 5` commands in a scratch directory: each command appeared about 1 s after it finished (one record each); afterwards the state became Sleeping, the composer was unlocked and "Worked for 39s" was shown.

## Read-only sessions falsely shown as interrupted at the end

- Cause: native history cannot distinguish "still running in another client" from "interrupted". When the Codex app-server rebuilds from a rollout, any turn without an end marker is reported as `interrupted` (a turn running in another process read as `interrupted` throughout and as `completed` only after it finished). Before an earlier fix, that summary was dropped only for turns the workbench ran itself, so every externally running Codex session ended with "Interrupted by user". For Claude, history loading did not treat an externally running session as having a turn in progress, so tools without results were closed as "Interrupted". Local rollouts: 2877 turns ended normally, 26 were genuinely interrupted (`turn_aborted`, all with reason `interrupted`), and none started without an end marker.
- After the earlier fix three cases remained: the frontend decided whether to close out history based on sidebar state (up to 10 s old); for Codex, reading the turn and determining running state were two separate reads, so a notice could appear at the boundary and never go away; tabs opened before an update kept running the old frontend.
- Fix: the history API returns a server-side `running` flag (a turn run by the workbench or still running in another client) and the frontend uses it to decide whether to close out. Followed records go straight to the adapter and are applied to the current state, so the real end of the same turn (for example `completed`) removes an earlier interrupted notice. The SSE connection first sends `hello` with a hash of the embedded `index.html`; if the version differs after a reconnect, the page shows "Workbench was updated" with a reload button.
- New Go race tests: history of an externally running Claude session returns `running: true`, then `false` after it finishes; the event stream sends `hello` with the build version first, and a different web build yields a different version. New Vitest test: a Codex turn first read as interrupted loses the notice once following reaches `completed`.
- Real reproduction: Playwright froze the sidebar list at its state before the turn started (simulating no refresh within 10 s), and `claude -p --resume` made an idle test session run `timeout 25 tail -f /dev/null`; the session was opened right after the tool call was written. The old build (main service) showed the session as Sleeping and the tool as "Interrupted" until the result was written 26 s later. The new build under the same conditions showed "Running…", a status line "Running Bash(…)", and switched to completed at the end. Reload notice: restarting the dev instance with a different web build while the page was open showed the notice after reconnecting.

## Terminal colors

- Basis: native transcripts contain plain Markdown only; colors come from each CLI's renderer and theme. From the Claude Code 2.1.322 binary: inline code and code blocks without a language use the `permission` color (dark `rgb(177,185,249)`, light `rgb(87,105,247)`); level-1 headings are bold italic and underlined, other headings bold; bold italic text is not colored; syntax themes are Monokai Extended (dark), GitHub (light) and the ANSI theme `ansi`, mapping highlight.js scopes to colors; 16 keywords such as `const`, `let`, `function`, `def` and `fn` use the `_storage` color. From the Codex TUI source (`markdown_render.rs`, `render/highlight.rs`): styles come from the syntax theme, default Catppuccin Mocha (Latte on light backgrounds); inline code (`markup.inline.raw`), heading levels, bold italic, links and quotes take colors from the tmTheme; only code blocks with a language are highlighted.
- Decisions: body text keeps a proportional font; Claude uses the default RGB theme; this round covers Markdown colors, code highlighting and ANSI in tool output.
- Implementation: the conversation area gets `data-agent`, and colors are CSS variables per agent and per light/dark theme. `rehype-highlight` is loaded lazily as a separate chunk (178 kB, 54.5 kB gzip) only when a block with a language is present, showing plain text first; the main chunk grew from 633.8 kB to 638.4 kB. The ANSI parser supports SGR reset, bold, dim, italic, underline, 16 colors, 256 colors and truecolor; other CSI and OSC sequences are stripped. `npm audit` reports 0 vulnerabilities.
- 7 new Vitest tests: ANSI styles and reset; bright, background, 256-color and truecolor; stripping non-color control codes and merging identical styles; `stripAnsi`; blocks with a language are highlighted and `const` is tagged as storage; blocks without a language or with an unknown language stay plain; inline code is not highlighted.
- Real data (isolated dev instance, dark and light): Claude inline code computed as `rgb(177,185,249)` / `rgb(87,105,247)`; in a `bash` block `cd` is Monokai green / GitHub blue and comments use each theme's comment color. ## In-session file paths, file manager and media viewer

When nothing matches it reports "not found: … (looked in game-demo/, ./)" while still matching `fs.ErrNotExist`. ## Engines stopped with the workbench showed "Error"

- Cause (event cache of a real Codex session): replacing the installed service at 11:00:36 stopped the session's loaded engine; its status went `idle → stopping → error` 6 ms later and stayed "Error" until the next message restarted the engine. Engine units are `BindsTo`/`After` the workbench's unit, so when the workbench stops, systemd stops them in the same transaction, and the workbench's own `systemctl --user stop` for the unit failed; `Stop` turned any stop failure into "error".
- Fix: `Manager.Shutdown` marks the workbench as closing and stops only sessions with an engine or previews; stopped that way, a session is "sleeping" (it resumes on its next message) and stop failures are not errors. `stopUnit` counts a failed stop as done when the unit is no longer active (`systemctl is-active` reports inactive, failed or unknown), waiting up to 3 s while it is still deactivating.
- New Go tests: a failed stop outside a shutdown is still an error; during `Shutdown` the loaded session ends up sleeping with its engine detached, and an unloaded session is left alone; `stopUnit` accepts stop failures for inactive, failed and unknown units.
- Claude has the same exposure, plus one more path. In the event cache no Claude engine was loaded during today's restarts (seven loaded Claude engines stopped outside a restart, all cleanly), but the code is shared, and a probe showed how each engine ends when systemd stops its unit (as it does first when the workbench's unit stops; `systemd-run --user --pipe --wait --collect`, stdin open, no model call): Claude Code exits with code 143 (`Main processes terminated with: code=exited, status=143`) and `systemd-run` returns 143; Codex exits 0. - Fix (exit path): `exited` treats SIGTERM/SIGINT deaths, exits 143/130 and exits during shutdown as stops (sleeping, no error row); any other non-zero exit is still an error. A stopped engine also releases its pending requests (`approval_resolved` per request, from both `exited` and `Stop`), and the page settles running tools when the session becomes sleeping, stopped or error, so a Claude AskUserQuestion cut off by a restart shows "Not answered" with Answer right away instead of a stale approval card and a spinner.
- Tests: `stoppedOnRequest` against real exits (`exit 143`, `exit 130`, `kill -TERM`, `kill -INT` are stops; `exit 1`, `exit 2`, `kill -KILL`, `kill -USR1` are not; the test avoids SEGV and ABRT, which leave a core dump); `exited` for a clean exit, Claude's 143, a terminated client, a crash (error with its row) and a crash during shutdown (sleeping), each releasing a pending request; a waiting AskUserQuestion settled to interrupted becomes an answerable question.
